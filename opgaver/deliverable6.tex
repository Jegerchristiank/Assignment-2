\subsection{Deliverable 6: Part II Reflections}
\label{sec:deliverable6}

\begin{enumerate}
\item \textbf{Initial exploration}
\textbf{Q1.a Data type in the log}\par
The file is a case-based radiology process event log. Each row is one event with case identifier, timestamp, activity label, actor, role, and optional clinical/technical context (e.g., modality, report-linked fields, notes). From exploration outputs in Appendix~\ref{app:part2_supporting}, Table~\ref{tab:d5_log_profile}, the dataset contains 150 events, 17 cases, and 12 unique logged activities (activity list in Appendix~\ref{app:d5_invisible_work}, Table~\ref{tab:d5_logged_activities}).

\textbf{Q1.b RQ use under good data quality}\par
If quality is good, the same structure supports all three research questions:
\begin{itemize}
  \item \textbf{RQ1:} timestamps and activity order allow bottleneck and turnaround-time analysis.
  \item \textbf{RQ2:} critical communication events can be checked for conformance and timeliness.
  \item \textbf{RQ3:} event traces can be transformed into candidate features for triage-model development.
\end{itemize}
The log is therefore fit-for-purpose in principle, but only under acceptable completeness, representativity, timeliness, and provenance quality.

\item \textbf{Method selection justification}
\textbf{Q2.a Completed method-selection table}\par
The completed table is included in Appendix~\ref{app:part2_supporting}, Table~\ref{tab:d5_method_selection}. Selected methods: \textbf{M2, M6, M8, M10, M11}.

\textbf{Q2.b Selected methods and rationale}\par
The selected set was chosen to cover all RQs with minimal overlap:
\begin{itemize}
  \item \textbf{M2:} baseline completeness gate before downstream interpretation.
  \item \textbf{M6:} representativity of urgency/shift context for generalisability.
  \item \textbf{M8:} direct safety-critical communication test (RQ2 core).
  \item \textbf{M10:} performance metrics with timestamp-credibility sensitivity (RQ1 core).
  \item \textbf{M11:} workload concentration patterns relevant to RQ1 and RQ3.
\end{itemize}

\textbf{Q2.c Deprioritised methods and rationale}\par
Methods were deprioritised mainly because of scope and overlap:
\begin{itemize}
  \item \textbf{M1:} useful schema check, but lower analytical value after basic integrity is confirmed.
  \item \textbf{M3:} ICD-11 format checks are useful, but missingness reduced immediate explanatory gain.
  \item \textbf{M4:} partly overlaps M11; M11 gave clearer workload concentration outputs.
  \item \textbf{M5:} modality case-mix useful, but less central than urgency/shift representativity for this report.
  \item \textbf{M7:} temporal-conformance value partly overlapped M10 timestamp-credibility analysis.
  \item \textbf{M9:} clinically relevant, but less central for cross-RQ synthesis in the selected scope.
\end{itemize}

\textbf{Q2.d Trade-offs considered}\par
Main trade-off: breadth versus depth. Running five methods gave full RQ coverage while keeping interpretation coherent rather than fragmented across too many partially redundant outputs.

\textbf{Q2.e RQ1--RQ3 influence on selection}\par
RQ1 drove M10 and M11, RQ2 drove M8, and RQ3 drove representativity/provenance emphasis (M6 plus interpretation from M2 and custom method). This ensured each RQ had at least one direct method and supporting cross-checks.

\item \textbf{Proposed DQ dimension}
\textbf{Q4.a Dimension definition}\par
The proposed custom DQ dimension is \textbf{operational authenticity}: whether logged traces represent real clinical workflow rather than test/training/administrative artifacts.

\textbf{Q4.b Motivation from exploration evidence}\par
In exploration code (Part 5), case \texttt{TEST-001} was flagged by multiple contamination signals: non-standard case ID, training/test marker in notes (\texttt{TRAINING CASE - DO NOT PROCESS}), administrative actor involvement, and a one-event trace. This pattern is not well covered by standard completeness/conformance checks but can bias downstream analysis.

\textbf{Q4.c Custom DQ assessment code}
\begin{lstlisting}[style=pycode,caption={Custom assessment method for operational authenticity},label={lst:d6_custom_method_inline}]
def my_custom_dq_method(df: pd.DataFrame) -> Dict[str, any]:
    """
    Assess operational authenticity (production-relevance validity).
    """
    rows = []

    for case_id, case_df in df.groupby('case_id'):
        reasons = []

        if not re.match(r'^CXR-\d{3}$', str(case_id)):
            reasons.append('Unexpected case_id format')

        if case_df['notes'].astype(str).str.contains(
            r'training|test|do not process', case=False, na=False
        ).any():
            reasons.append('Training/test markers in notes')

        if case_df['actor'].eq('Admin User').any():
            reasons.append('Administrative/test actor involvement')

        if len(case_df) < 3:
            reasons.append('Extremely short trace (low operational realism)')

        score = len(reasons)
        if score >= 3:
            risk_level = 'high'
        elif score >= 1:
            risk_level = 'medium'
        else:
            risk_level = 'low'

        rows.append({
            'case_id': case_id,
            'risk_level': risk_level,
            'risk_score': score,
            'reasons': '; '.join(reasons) if reasons else 'None',
            'event_count': len(case_df),
        })

    case_flags = pd.DataFrame(rows).sort_values(
        ['risk_score', 'case_id'], ascending=[False, True]
    )
    flagged = case_flags[case_flags['risk_level'].isin(['high', 'medium'])].copy()

    summary_metrics = {
        'total_cases': int(len(case_flags)),
        'flagged_cases': int(len(flagged)),
        'flagged_case_rate_pct': round(
            100 * len(flagged) / len(case_flags), 2
        ) if len(case_flags) > 0 else 0.0,
        'high_risk_cases': int((case_flags['risk_level'] == 'high').sum()),
    }

    return {
        'case_flags': case_flags,
        'flagged_cases': flagged,
        'summary_metrics': summary_metrics,
    }
\end{lstlisting}

\textbf{Q4.d RQ impact and mechanism}\par
Summary results (Appendix~\ref{app:d5_custom_dimension}, Table~\ref{tab:d5_custom_summary}) show 1 high-risk flagged case out of 17 (5.88\%). Even this small share affects all RQs:
\begin{itemize}
  \item \textbf{RQ1:} can distort apparent workflow timing and throughput metrics.
  \item \textbf{RQ2:} can alter conformance denominators and bias pass/fail interpretation.
  \item \textbf{RQ3:} can contaminate model-development data and reduce validity.
\end{itemize}

\textbf{Q5.a Data facet findings, issues, and RQ consequences}
\begin{itemize}
  \item \textbf{Revealed by methods:} M2 missingness profile and M10 timestamp sensitivity.
  \item \textbf{Main issues:} high field sparsity and unstable timing-based estimates under credibility checks.
  \item \textbf{Consequences for RQs:} weaker confidence in RQ1 performance estimates and RQ3 feature reliability.
\end{itemize}

\textbf{Q5.b Source facet findings, issues, and RQ consequences}
\begin{itemize}
  \item \textbf{Revealed by methods:} custom dimension plus M2 context sparsity.
  \item \textbf{Main issues:} provenance contamination risk (e.g., \texttt{TEST-001}) and inconsistent source-level completeness.
  \item \textbf{Consequences for RQs:} reduced transferability and training-data trust, especially for RQ3.
\end{itemize}

\textbf{Q5.c System facet findings, issues, and RQ consequences}
\begin{itemize}
  \item \textbf{Revealed by methods:} M8 communication conformance and M10 batch-logging warnings.
  \item \textbf{Main issues:} logging design and entry behavior strongly influence apparent process reality.
  \item \textbf{Consequences for RQs:} RQ1 and RQ2 can be biased if logged time is treated as exact work time.
\end{itemize}

\textbf{Q5.d Task facet findings, issues, and RQ consequences}
\begin{itemize}
  \item \textbf{Revealed by methods:} M6 urgency/shift skew and M8 threshold-based conformance.
  \item \textbf{Main issues:} task-pattern imbalance and policy-threshold dependence.
  \item \textbf{Consequences for RQs:} efficiency/safety conclusions may partly reflect case mix and rule settings.
\end{itemize}

\textbf{Q5.e Human facet findings, issues, and RQ consequences}
\begin{itemize}
  \item \textbf{Revealed by methods:} M11 workload concentration; M10/custom hints about documentation behavior.
  \item \textbf{Main issues:} concentration and human logging practice shape what becomes visible.
  \item \textbf{Consequences for RQs:} RQ1 bottleneck interpretation and RQ3 assumptions can be role-biased.
\end{itemize}

\textbf{Q5.f Most challenging facet and reason}\par
The \textbf{Human} facet was most difficult. Event logs capture actions but rarely intent, negotiation, and informal coordination. The \textbf{Source} facet was also difficult because provenance questions often require context outside the event table.

\textbf{Q5.g Alternative assessment options}
\begin{itemize}
  \item Add explicit provenance metadata (production/test flag, entry mode, user context).
  \item Triangulate with linked systems (RIS/PACS/message logs) for cross-source validation.
  \item Use targeted mini-interviews or debriefs for anomalous cases.
  \item Run periodic audits on documentation practice and timing behavior.
\end{itemize}

\item \textbf{Invisible work and system design implications}
\textbf{Q6.a Invisible-work table reference}\par
The completed table is included in Appendix~\ref{app:d5_invisible_work}, Table~\ref{tab:d5_invisible_work}, grounded in workflow Figure~\ref{fig:assignment2_fig1} (Appendix~\ref{app:assignment_workflow_figure}). Included activities: radiologist-to-radiologist consultation, clarification call to ordering clinician, informal reprioritisation/handoff, and cross-team coordination on patient readiness.

\textbf{Q6.b Why activities may be unlogged (technical/social/economic)}\par
Across the listed activities, missingness is plausibly explained by:
\begin{itemize}
  \item \textbf{Technical:} phone/verbal and cross-system interactions often lack a shared event schema.
  \item \textbf{Social:} informal coordination is situational and intentionally lightweight.
  \item \textbf{Economic/workload:} complete micro-documentation increases workload and may reduce throughput.
\end{itemize}

\textbf{Q6.c Log-only model limitations and RQ consequences}\par
If modeling relies only on logged events, the model misses real coordination pathways:
\begin{itemize}
  \item \textbf{RQ1:} bottlenecks can be misattributed because hidden coordination delays are not represented.
  \item \textbf{RQ2:} safety communication may appear stronger than practice if verbal escalation is invisible.
  \item \textbf{RQ3:} AI models may learn an oversimplified process missing key real-world coordination behavior.
\end{itemize}

\textbf{Q6.d Part I parallel: interview vs observation}\par
This mirrors Part I directly: interview captured work-as-imagined, while observation captured work-as-done with deviations and ad hoc coordination. Here, event logs capture work-as-recorded, which is again only a partial view of practice.

\textbf{Q6.e Implication for data-driven healthcare IT}\par
The gap shows that data-driven design is necessary but insufficient on its own. In Chapter 9 terms, formal systems encode codified work, but clinically important informal coordination can remain outside system boundaries \parenciteshort{guidehealthinformatics2026ch9and27,guidehealthinformatics2026ch27}.

\textbf{Q6.f Concrete logging change, trade-offs, and mitigation}\par
One concrete change is a lightweight \texttt{coordination\_interaction} event type at high-impact points (e.g., escalation, reprioritisation, cross-team handoff), with minimal fields: timestamp, linked case ID, initiating role, receiving role, reason code. Trade-offs: more documentation burden and possible surveillance concerns. Mitigation: selective (not universal) capture, role-based visibility, and governance that uses logs for process improvement rather than individual blame.
